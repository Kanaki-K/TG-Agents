# Операционка: бэкапы и «жив ли завод»

Короткий рунбук для владельца. Закрывает AUDIT N-5/P2-14 (бэкап невосстановимого) и «упавший бот молча мёртв».

## 🔴 Невосстановимые файлы — БЭКАПИТЬ РЕГУЛЯРНО

Всё это вне git (в `.gitignore`) и живёт только на твоей машине. Потеря = катастрофа разного масштаба:

| Файл | Что на нём | Потеря = |
|---|---|---|
| `data/mtproto.session` | MTProto-учётка (бёрнер) | вся выгрузка канала + разведка ТГ + **публикация**. Восстановление = повторный логин по SMS + риск для аккаунта |
| `.env` | все секреты (токены ботов, API-ключи, X-куки, CMC) | завод не стартует; перевыпуск всех ключей |
| `data/threads_token.json` | Threads-токен (авто-refresh) | доступ к Threads; нужен повторный OAuth-бутстрап (окно refresh 60 дней) |
| `data/gpt_profile/` | бёрнер-профиль ChatGPT (обложки флагмана) | повторный логин в веб-ChatGPT |
| `data/published_flagships.jsonl` | журнал ВЫШЕДШИХ флагманов — вход Threads-дистиллятора (датированная история; драфты эфемерны, этот файл — нет) | мини-флагману нечего дистиллировать; история публикаций утрачена |
| `data/threads_my_replies.json` + `data/psychotype_notes.md` + `data/threads_psychotype.md` | корпус живого голоса (4966 реплик) и его ручная LLM-выжимка (17 партий) | пересоздание = сотни API-запросов + дни работы и $ |
| `data/plan_settings.json` | расписание, настроенное ИЗ ЧАТА (дни/время выхода, лид автопилота) — перекрывает `.env` | канал вернётся к расписанию из `.env`/дефолта кода (17:00 вместо твоего 16:00) |
| `memory/` (живое) | `scope_lessons.md`, `post_lessons.md`, `threads_lessons.md`, `headline_bank.md`, `flagship_topics.md`, `x_authors.json`, `briefs/`, `drafts/`, `threads_drafts/` | обученность агентов и состояние (gitignored — в репо их НЕТ) |

## Как бэкапить

**Основной способ — одной командой (кросс-платформенно):**

```
python backup.py "D:\Cloud\tg-agents"     # ← путь к облачной папке / внешнему диску
```

Создаёт `tg-agents-backup-<дата-время>.zip` со ВСЕМ незаменимым (список — в самом `backup.py`, это единый
источник правды «живое vs скретч», N-3). Регенерируемый скретч (выгрузки/обложки/таблицы) намеренно НЕ
включается — пересобирается `refresh.py`. Посмотреть классификацию без архива: `python backup.py --list`.
Без аргумента архив ложится в `./backups/` (gitignored) — но держи копию ОФФ-машинно (облако/внешний диск).

**Альтернатива (PowerShell, если нет Python под рукой):**

```powershell
$stamp = Get-Date -Format "yyyy-MM-dd"
$dst = "$HOME\Backups\tg-agents"
New-Item -ItemType Directory -Force $dst | Out-Null
Compress-Archive -Path .env, data\mtproto.session, data\threads_token.json, data\gpt_profile, memory `
                 -DestinationPath "$dst\tg-agents-$stamp.zip" -Force
```

Держи 2-3 последних архива. **Проверь восстановление хоть раз** (распакуй в чистую папку, запусти `--draft-only`).

## Как понять, что завод ЖИВ (silent-failure чек)

Боты/пайплайн падают молча. Быстрая проверка:

```powershell
# 1) был ли расход за последние сутки (если пусто — ничего не гонялось)
Get-Content data\cost_log.jsonl -Tail 3

# 2) свежесть последнего брифа и драфта (старьё = разведка/письмо встали)
Get-ChildItem memory\briefs\*.md, memory\drafts\*.md | Sort LastWriteTime -Desc | Select -First 2 Name, LastWriteTime

# 3) сухой прогон без публикации — «всё ли живо end-to-end»
python run_pipeline.py --scope --draft-only
```

Признаки тихого отказа: `/scan` пишет «⚠ X недоступен» (протухли куки → перевзять), нет свежих брифов в дни разведки (Пн/Вт/Чт), пустой `cost_log` за сутки при ожидаемых прогонах.

## 🤖 Автопилот (флагман + скоуп): включён ли, как остановить

Оба формата умеют запускаться сами и включаются НЕЗАВИСИМО: флагман (Вт/Чт) и скоуп 🔭 (Пн/Ср/Пт),
выход обоих в 16:00, старт за 4ч. Полное описание, настройка и чек-лист — [AUTOPILOT.md](AUTOPILOT.md).
Операционный минимум:

- **Включён?** `python run_autopilot.py --status` — сводка по обоим форматам + панель на каждый.
  Выключатели — файлы `data/autopilot_on_flagship` и `data/autopilot_on_scope` (нет файла = формат
  спит; по умолчанию выключены оба).
- **Стоп-кран:** `Remove-Item data\autopilot_on_scope` (или `…_flagship`), либо разом
  `python run_autopilot.py --uninstall`. Уже идущий прогон этим не остановить — там стоп-кран
  другой: удалить пост из «Отложенных» канала.
- **Тишина в день выхода** = либо ПК спал (журнал Планировщика задач), либо `/test`-режим, либо слот
  уже был занят, либо (только скоуп) не нашлось свежего повода. Все случаи видны в `--status`; про
  режим, отсутствие канала и «повода нет» автопилот пишет в Telegram сам.
- **Метка последнего авто-прогона:** `data/autopilot_state.json` (не бэкапится — восстановимо, это
  просто дата). Свой лог — `data/autopilot.log` (тоже не бэкапится, с ротацией).
- **Выключатель НЕ бэкапится намеренно:** после восстановления на новой машине автопилот должен быть
  ВЫКЛЮЧЕН — иначе он тихо начнёт публиковать в канал ещё до того, как ты всё проверил.

## 🧵 Threads: стоп-кран, лимиты, «почему молчит»

После проверки аккаунта 14.07 сеть Threads закрыта **ПО УМОЛЧАНИЮ** — это осознанный предохранитель
(`connectors/threads/_guard.py`, там же вся история «зачем»). Как это работает:

- **Открыть сеть:** создать пустой файл `data/threads_unlocked` (например, `New-Item data\threads_unlocked`).
  Нет файла → ЛЮБОЙ запрос к Threads = отказ с объяснением. Удалить файл = мгновенно всё закрыть.
- **Бюджеты:** максимум запросов за прогон и за скользящие сутки (по умолчанию **200/500**, можно
  менять через `THREADS_RUN_BUDGET`/`THREADS_DAY_BUDGET`). Подняты 17.07 с 60/150: прежние душили
  рядовой сбор (~50-120 запросов) — он упирался в лимит на комментах и по «фейл-закрыто» выбрасывал всё
  (гонял вхолостую). 200/500 всё ещё ~1% пола Meta (48 000/сутки); упёрлись — прогон встаёт, недобор
  доберёт следующий (добор «долгов» в `collect`). Настоящий предохранитель — не эти счётчики, а
  стоп по квоте Meta (ниже).
- **Предохранитель (ГЛАВНЫЙ):** первый признак лимита от Meta (429/коды лимита или `x-app-usage` ≥ 80%)
  = стоп всего прогона + файл-заморозка `data/threads_cooldown` на время остывания. НЕ удаляй его руками
  без причины — он истекает сам.
- **Журнал + сводка:** каждый запрос пишется строкой в `data/threads_api_log.jsonl`; в конце сбора
  печатается сводка `run_summary` — сколько запросов, **куда** (лента/метрики/комменты), дневной
  остаток, пик квоты Meta. «Сколько куда ушло» видно сразу.
- **Темп:** паузы 1.5-4с между запросами + передышки 8-20с (ускорено 17.07 с 4-11с/30-120с — рядовой
  сбор был ~20 мин, стал ~3-4). ~0.3-0.7 запр/сек — вежливо и далеко от per-second лимита Meta.

**Запись (посты/ответы) — ОТДЕЛЬНЫЙ второй ключ.** Каждый пост/ответ — публичное действие,
поэтому чтение и запись развязаны: открыл чтение — запись НЕ открылась «заодно».

- **Открыть запись:** `python -c "from connectors.threads import _guard; _guard.unlock_write('обкатка вехи E')"`
  (причина обязательна — остаётся в файле `data/threads_write_unlocked`). Нужны ОБА ключа.
- **Закрыть запись:** удалить `data/threads_write_unlocked` (чтение не тронется).
- **Бюджеты записи:** 10 за прогон / 24 за сутки (~12 публикаций: пост = контейнер+publish
  = 2 запроса), пауза 30–75с между записями. Это ~1–2% лимитов Meta (250 постов + 1000
  ответов/24ч) — «меньше, но качественнее» зашито числом. Поднять: `THREADS_WRITE_*` в окружении.
- **Перед публикацией:** `python -m connectors.threads.publish --check` — фактическая квота
  записи глазами Meta + состояние защиты. Публикация руками: `--post "текст"` (спросит «да»),
  ответ: `--reply-to <id> --post "текст"`, репетиция без сети: `--dry-run`.
- **Линт охвата жёсткий:** пост со ссылкой или хештегом НЕ уйдёт (охват режется ~×5 — данные
  наших 434 постов). Это правило кода, не пожелание.

**«Threads молчит / не собирается» — чек по порядку:**
1. Есть ли `data/threads_unlocked`? Нет → сеть закрыта, это не поломка (создай файл).
2. Есть ли `data/threads_cooldown`? Есть → предохранитель остывает, подожди (или посмотри в журнале, что его выбило).
3. Хвост журнала: `Get-Content data\threads_api_log.jsonl -Tail 5` — видно последний запрос и ответ.
4. Логи про токен: warning «не смог обновить токен Threads» = refresh ломается, разберись ДО истечения
   60 дней (иначе повторный бутстрап: `python -m connectors.threads.auth --manual`).
